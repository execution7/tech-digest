🔥 主故事

一个推荐榜，暴露了“替你选工具”里缺失的问题

同样问“推荐一个工具”，换一个模型，默认答案就可能换一套。

9月7日，Latent Space 介绍 Frontier AEO Tracker：用多种问法观察模型在不同产品类别中推荐谁，并提供可检查的提示与答案。作者报告覆盖7个模型、161个类别，每类使用6种提示变化；这些数字描述其研究设计，不是独立复现的行业统计。

核心冲突作者观察到，部分模型更常推荐与自身生态接近的编码工具。但“经常被推荐”测量的是回答倾向，不是安装成本、你已有的能力，更不是你在 iOS、Android 或 Web 项目中能省多少时间。
转折点研究还比较了改写问题后的选择变化，并承认样本与工具调用可见范围有限。它更适合让我们检查推荐依据，而不是再把榜单第一名装一遍。AEO 即答案引擎优化，讨论的是产品怎样出现在 AI 答案里。
为什么是现在原文发表于9月7日，进入本期72小时新闻窗口。它恰好解释了一个常见体验：回答很流畅，推荐却没有贴着真实工作走。
对团队的启发下一次选工具，只给一个真实任务，并要求同时列出“不安装也能做的方案”和“新增工具的必要性”。把安装、版本、权限与效果分别核查。

我的判断：我的判断：推荐前先补三个条件。第一，当前卡在需求判断、代码清理还是回归定位；第二，是否必须留在本机、能否接新服务；第三，完成后用什么证据验收。把这些条件写进问题，比要求模型再列十个热门产品更可能得到可采用的答案。

推荐次数回答“它常想到谁”，验收证据才回答“它帮到了谁”。

3、Swift Package Index：隐藏兼容性信息，不等于不兼容 confirmed

事实边界：与前期未来时间戳修复是不同变更。仅核对提交，不断言线上开关当前启用。

🛠️ 工具推荐

实践精选已有能力可用

今日实用工具：grilling Skill，先问清再动手

如果需求看起来都懂，做出来却总要返工，可以让现有 Skill 先追问尚未确定的决策。它沿着依赖关系拆问题，能查证的事实先查，把需要你拍板的选择留给你。这里补充的是同一技能库的决策追问能力，不是重复报道技能库发布。

适合你的环节：需求评审、技术选型、跨端方案取舍；避免把未确认假设直接实现。

今天怎么试：直接说：用 grilling 帮我确认这个需求，只问最影响实现的三个决策，一次一个；没确认前不要改代码。完成后留下决策、待确认项和验收条件。

边界：本机说明按一次一问；上游当前改为按依赖轮次提问，两者不是同一版本。限制问题数量，别让澄清变成长访谈；不替产品做决定。

实践精选已有能力可用

research Skill：把“听说支持”变成可追溯结论

遇到某 SDK 是否支持 iOS、MCP 是否会写文件等问题，让它回到官方文档、代码和 API 查证，整理成一份带链接的 Markdown。价值是省去找原文和汇总证据的往返，不是让模型替你猜兼容性。已有实践，不是当日新发布。

适合你的环节：客户端接入评估、SDK兼容性、API权限与工具安装前检查。

今天怎么试：直接说：用 research 核实这个 MCP 能读写哪些数据、是否支持本机环境、最小接入步骤是什么；只查第一方资料，保存一份结论，不安装。

边界：本地技能设计会安排后台研究，仍消耗 Token；只给一个明确问题和输出范围。文档支持不等于你的账号有权限，不发送私有源码到陌生服务。

实践精选方法可试

git bisect：缩小“从哪个提交开始坏”的范围

有一个确定正常的提交和一个确定异常的提交时，Git 可以二分挑选中间版本，逐步缩小首次引入问题的范围。适合比“把最近所有提交交给 Agent 猜”更可重复的回归定位。这是已有 Git 工作法，不是新装软件。

适合你的环节：iOS/Android/Web 的稳定可复现回归；需要可靠的正常与异常判据。

今天怎么试：直接说：为这个回归制定 git bisect 方案，先确认正常与异常提交，以及每一步的判定方法；只给方案，不切分支、不编译。正式执行应在独立干净工作区。

边界：默认会切换提交；不能直接在有未提交改动的工作区尝试。偶发问题和外部环境变化会误导二分，无法判定的版本要跳过。不是普通只读 diff。

实践精选条件适用

Knip：先检查 JS/TS 冗余，再让 Agent 解释

Knip 通过项目入口、依赖图和框架配置寻找未使用文件、导出与依赖。比让模型读遍仓库猜“哪些能删”更适合作为结构化起点。9月8日 X 开源讨论带出该项目，项目本身早已存在，不包装成新品。

适合你的环节：Web、Node脚本与JS/TS工具仓库的依赖清理；不是Swift/Kotlin原生代码分析器。

今天怎么试：先在隔离分支按官方入口接入，运行报告但不自动修复；把前五个可疑导出交给 Agent 核对真实调用。用“确认入口→生成报告→逐项复核”的顺序试一次。

边界：当前 PATH 未发现 knip，项目依赖未检查。动态导入、脚本入口和插件配置会影响结果；本期没有安装，不使用 --fix 自动删除，也不承诺具体 Token 节省。

9月7日更新条件适用

LLM 0.35：把模型调用接到已有脚本

9月7日的0.35更新新增 gpt-6-astra 模型标识。LLM 是命令行模型调用工具，适合把一段脱敏日志或固定输入纳入可重复脚本。只有确实需要批量、可重复调用时才考虑它，日常聊天不必再装一个壳。

适合你的环节：自动化脚本中的固定输入分析、对照提示与批处理原型。

今天怎么试：先确认模型API权限、费用与日志保存策略，再按官方文档安装。用一段自造的错误日志做单次调用，检查结果和用量；不要直接读取公司的整份日志。

边界：当前 PATH 未发现 llm。加入模型名称不代表账号有 Astra 权限；API调用可能计费，输入输出日志也需要管理。未安装、未调用、未实测效果。

🧩 本期概念库

1. AEO：答案引擎优化

一句话解释：研究产品如何被AI答案提及或推荐。

为什么重要：它测回答倾向，不天然等于质量、适配度或市场份额。

团队应用：工具推荐要求提供第一方依据和采用条件。

2. 决策依赖

一句话解释：一个选择必须等另一个选择确定后才有意义。

为什么重要：前提没确认时并行实现，会把同一歧义扩散到多端。

团队应用：先确认状态语义，再确认接口与页面表现。

3. 二分定位

一句话解释：利用已知正常与异常边界，不断缩小引入变化的范围。

为什么重要：可重复判据比一长串可疑提交更有帮助。

团队应用：保留稳定复现步骤，在独立工作区查回归。

4. 观察时间与发生时间

一句话解释：今天看到一个链接，不表示其中的事件今天发生。

为什么重要：聚合站和订阅时间容易把旧事包装成新事。

团队应用：报告分别标明发布时间、实验时间和发现时间。

🎙️ 播客提纲

Agent推荐的工具，未必是你需要的工具

你问 Agent，有没有能让我提效的工具，它给你列出一个新编辑器、一个数据库平台，再加一套云服务。看上去都不错，但你真正想省的，可能只是发布前那十分钟重复检查。今天的科技情报，就从这个错位讲起：模型常推荐什么，和你实际需要什么，是两件事。

主故事：先看推荐在测什么

九月七日，Latent Space 介绍了一个观察模型产品选择的研究项目。它用不同问法，看模型在多个类别里推荐谁。作者报告覆盖七个模型、一百六十一个类别，并让提示出现六种变化。这些是项目描述的研究范围，不是我们独立复现的结果。作者观察到，部分模型偏爱与自身生态接近的编码工具；同时也承认，样本和可见工具调用存在限制。这里最值得带走的，不是榜单第一名，而是一个问题：这个答案到底是在测产品质量，还是模型想到某个名字的概率？我的判断是，工具推荐先要写明具体任务、允许的权限，以及什么叫完成。否则再强的模型，也可能把通用热门答案当成你的个人方案。

快讯一：两项已有Skill，不用重新安装

今天先用你已有的两个 Skill。grilling 用来追问决策，例如一个取消操作，到底只是关页面，还是要停止后台请求。直接要求它只问三个关键问题，一次一个，没确认前不要改代码。要注意，本地说明与上游最新问答节奏不完全一致，本期没有升级。research 则适合查证：一个 SDK 是否支持目标平台，一个 MCP 会读写什么数据。把范围限定为一个问题，要求回到官方文档和代码，留下带来源的结论。它仍然消耗 Token，不适合拿来无限泛搜。

快讯二：Git帮你缩小回归范围

第三项是 git bisect，也就是二分定位。你提供一个确定正常的提交和一个确定异常的提交，它不断选择中间版本，让判定范围逐步缩小。本机已经有 Git，不需要另装产品。但它默认会切换代码版本，不是普通的只读比较。先准备可靠的复现判据，再用独立干净工作区；今天可以先让助手制定方案，不要直接在有未提交改动的业务目录操作。偶发问题也不能硬套二分。

快讯三：两个需要接入的小工具

Knip 面向 JavaScript 和 TypeScript，查未使用的文件、导出和依赖。它适合 Web 或脚本仓库，不是 Swift 和 Kotlin 的通用分析器。先生成报告，再逐项复核，不要自动删除。另一个是 LLM 命令行工具，九月七日的零点三五版本增加了 Astra 模型标识。它适合把固定输入接进脚本；加入模型名称不等于账号就有权限，还要确认API费用和日志策略。这两项当前都没有确认安装，本期也没有替你安装。

团队行动：把不安装方案也写进去

其他动态里，Kotlin 的更新提醒我们先核对兼容性；Swift Package Index 的显示开关提醒我们，没有显示不等于测试失败。数据库 MCP 教程则提醒，参数转义和服务端预备语句不是一个概念。今天可以给工具推荐加一条硬要求：同时给出不安装也能做的办法，说明新增工具到底省掉哪一步，再决定是否值得接入。旧文实践与近期更新在正文里分开标注，不把社区转发日期当成事件日期。

先选一个小任务试用：需求说不清，就追问决策；能力不确定，就查原始依据；回归定位太慢，就准备二分判据。今天不需要把五个工具都装上，你需要的是一次能看出差异、也能停止和回退的验证。

✅ 对团队的启发

1

下一项需求先用已有 grilling，只问三个关键决策；未确认前不改代码。

2

接入SDK或MCP前，用 research 查原始文档：平台、权限、数据去向、退出方式。

3

一次稳定回归先准备正常/异常提交与判据，再决定是否在独立工作区二分。

4

JS/TS工具仓库有冗余问题时才评估 Knip；模型CLI有批处理需求时再评估 LLM。
