🔥 主故事

旧系统很难改，不代表重写一套就会更容易

决定重写的时候，旧系统往往还在接业务需求。新系统的终点，也就一直在移动。

Simon Willison 在 9 月 6 日回应一场技术债讨论：按照他的经验，另起炉灶可能留下两套生产系统，一套继续承接业务，另一套只覆盖部分功能。这里讲的是作者经验，不是一次已定责事故或行业统计。

核心冲突新代码更容易生成，但新旧行为是否一致，仍然要逐项证明。单看重写进度，容易漏掉旧系统还在变化这件事。
转折点作者给出的倾向是先为旧系统增加自动化测试，再判断定向重构能否达到目标，而不是一开始就宣布整套替换。
为什么是现在这段评论发布于 9 月 6 日 09:08 UTC，进入本期 24 小时窗口；下方工具和教程是实践精选，不作为当日新版本报道。
对团队的启发选一个待改的 Kotlin 符号，先列引用和必须保持的行为；只改这一处，再用测试与代码审查核对影响。

我的判断：对 Agent 辅助开发，我更愿意先缩小一个真实改动：弄清引用关系，固定行为边界，观察运行状态，再验收差异。工具帮助搜集证据，不能替团队决定所有系统都该重构或重写。

先让旧行为可检查，再决定新代码该写多少。

来源：simonwillison.net

🛠️ 工具推荐

MCP · 实践精选条件适用

今日实用工具：Kotlin PSI MCP

通过 MCP 把 IDE 的 Kotlin 语义分析交给 Agent：查引用、跳到定义、探索继承关系。它不是另装一个大 IDE，而是为已有 Android Studio 或兼容 IDE 增加一个小接口。已有项目，本期作为实践精选。

适合你的环节：Android 引用排查、重构前影响分析和审查准备。

今天怎么试：先选择一个 Kotlin 符号，用已有 IDE 记录引用结果；确认插件版本和接入权限后，再用 PSI MCP 查询同一符号，比较是否遗漏。

边界：需要安装插件、重启 IDE、打开正确工程并完成索引，再配置本地 HTTP MCP。未安装或连接验证；跨语言支持有限，不能把它当成所有语言的通用分析器。

调试 · 实践精选条件适用

Compose Recomposition Highlighter

项目提供 Compose 重组计数、颜色热区和热点列表，帮助开发者在页面上看见重复渲染的位置。它提供排查线索，不自动证明某处存在用户可感知的性能问题。已有项目，本期作为实践精选。

适合你的环节：Compose 测试页面的重组定位与性能排查。

今天怎么试：仅在明确的 Compose 测试页面评估接入，对比相同交互下的计数与帧表现；保留无插件基线，不带入生产发布。

边界：需要项目依赖与测试构建适配，未安装或运行。零开销属于项目说法，未经独立测量；高重组次数不能单独证明卡顿。

🧩 本期概念库

1. 语义索引

一句话解释：记录符号实际定义和引用关系，而不只是匹配字符串。

为什么重要：同名符号和重载会让纯文本结果混在一起。

团队应用：先确定工程与索引状态，再用引用清单指导小范围改动。

2. 观察指标与验收指标

一句话解释：前者帮助定位现象，后者用来判断目标是否达成。

为什么重要：重组次数是线索，不等于帧耗时或体验结论。

团队应用：每个可视化指标都配一个独立的结果核对。

3. 组合式测试准备

一句话解释：把初始化、约束控制和清理封装为可组合的测试辅助件。

为什么重要：减少样板代码，同时避免测试基类承担越来越多职责。

团队应用：从现有重复步骤提取规则，保留失败时的状态与清理证据。

🎙️ 播客提纲

先查清引用，再让 Agent 改代码

改一个函数之前，你最想知道什么？不是整个仓库里有多少行出现了相同的名字，而是哪些调用真的会被这次改动影响。今天是精选短版，不凑新版本数量。我们围绕一个问题展开：怎样让 Agent 在动手之前，先拿到足够好的证据。

主故事：重写之前，先固定旧行为

先看 Simon Willison 在九月六日的一段讨论。他描述了一种风险：团队觉得旧系统技术债太多，于是开始重写；但业务不会停下来，旧系统仍然在改，新系统可能只接住部分功能。结果不是立刻告别旧代码，而是需要同时维护两套系统。这是作者的经验，不是说所有重写都会失败。他更倾向于先给旧系统补自动化测试，再看小范围重构能不能解决问题。我的理解是，Agent 让生成代码更容易，却不会自动替我们证明新旧行为一致。所以这期工具的共同点，不是替你写更多，而是帮你看清将要改什么，以及改完怎么检查。可以先选一个真实的小改动，记录它的调用方、必须保留的返回结果和错误路径，再限定修改范围。不要把重写代码的速度，直接当成项目交付的速度。

工具一：把 IDE 的理解交给 Agent

Kotlin PSI MCP 做的，是把 IDE 的语义分析通过 MCP 交给助手。查引用、找定义、看继承关系，都比只搜相同文字更贴近代码实际结构。但它不是装上就能分析任何仓库：需要兼容的 IDE 插件，打开正确工程，并且完成索引。我们没有替你安装。最小验证方法，是先用现有 IDE 查一个 Kotlin 符号的引用，再在接入后查询同一个符号，看结果是否一致。今天推荐的是这个接口，不是让你换一整套开发环境。

工具二：先看见重组，再判断卡顿

第二项是 Compose 重组可视化。项目提供计数、颜色热区和热点列表，适合在测试页面上缩小排查范围。不过这里必须分开两件事：某个组件重组很多，和用户真的感觉卡顿，不是同一个结论。还需要对照帧表现和真实交互。项目宣传的零开销，我们没有独立测量，所以也不会当作保证。两个小工具都是实践精选，不是声称今天刚发布；需要接入的，就明确标为条件适用。

实践：从最小边界减少重复

这期还放了两篇背景教程。一篇把 WorkManager 测试的重复准备封装成可组合的规则，另一篇在一个 JVM 小工具里替换手写的 Gemini 请求。它们不是今天的新消息，但有一个可迁移的方法：先找边界清楚、重复发生的一小块。测试规则要适配实际测试框架，SDK 案例也不能不检查就搬进客户端。真正该减少的是重复工作，不是权限检查、失败处理和验收。

团队行动

今天先不装工具也能做一件事：把下一次改动的目标符号、不变行为和验证办法写成一段短说明，再让已有的审查技能检查遗漏。后续评估 MCP 时，不把安装成功当成接入成功，而是对照一次真实查询。评估重组工具时，保留没有插件的基线，避免观察手段改变了你要观察的现象。这样做得到的不是一张更长的软件清单，而是一条更短、更清楚的验证路径。

这期的判断很简单：先让证据更清楚，再让改动更快。能现在用的方法今天就用，需要安装和验证的工具先说清条件，不靠增加软件数量制造提效感。

✅ 对团队的启发

1

立即可用的是工作方法：给下一次改动写清目标符号、不变行为和验收证据，再调用已有审查技能。

2

新 MCP 先核对项目、权限与输出一致性；没有安装或接入验证时，只标条件适用。

3

可视化排查先留无插件基线，不用一个颜色或计数替代性能验收。
