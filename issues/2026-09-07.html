第 92 期：让 Agent 少返工，比让它多写代码更有用

第 92 期 · 2026年9月7日，星期一 · 72小时增补版

我的判断：先减少需求歧义、上下文丢失和验收盲区，再追求生成速度；一个接入现有流程的小工具，往往比换一套开发环境更有价值。

✨ 本期亮点：6项工具与工作法：domain-modeling、prototype、git range-diff，以及 Agent Browser、OKF Agent Memory、Kotlin PSI MCP · 前两项 Skill 当前会话已提供；Git 已确认存在。另三个项目需要接入验证，不冒充已安装可用 · 9月4日至7日的未重复动态补充进来：Codex 异步澄清修复、Bun 上下文保留回归、Kubernetes Rootless Beta · X 工具线索已回溯原始仓库；同名 Agent Browser 项目、记忆工具的节省宣传和模型权限均保留边界

Kotlin PSI MCP 第一方仓库的配置界面。它依赖已打开并完成索引的工程；图片不是本机安装或运行证明。

🔥 主故事

旧系统很难改，不代表重写一套就会更容易

决定重写的时候，旧系统往往还在接业务需求。新系统的终点，也就一直在移动。

Simon Willison 在 9 月 6 日回应一场技术债讨论：按照他的经验，另起炉灶可能留下两套生产系统，一套继续承接业务，另一套只覆盖部分功能。这里讲的是作者经验，不是一次已定责事故或行业统计。

核心冲突新代码更容易生成，但新旧行为是否一致，仍然要逐项证明。单看重写进度，容易漏掉旧系统还在变化这件事。
转折点作者给出的倾向是先为旧系统增加自动化测试，再判断定向重构能否达到目标，而不是一开始就宣布整套替换。
为什么是现在这段9月6日的原文进入本期72小时窗口。近期动态标明原始发布日期，工具实践另列，不冒充新品。
对团队的启发下一项需求先澄清三个容易混用的名词，只验证一个状态转换；代码提交后比较前后两轮补丁。

我的判断：把这条经验用在 Agent 协作上，我更关注三个返工入口：名词没对齐、状态没演示、改动没比较。先用已有 Skill 收紧前两项，再用范围比较和浏览器证据做验收；不要先采购一整套新环境。

先让旧行为可检查，再决定新代码该写多少。

来源：simonwillison.net

少填几项配置，可能意味着把更多运行责任交给服务方。

9月5日的作者体验比较托管 Agent 电脑与用户自管 Gateway：前者减少连接配置，后者保留环境控制。适合学习两种责任划分，不作为你的账号可用性证明，也不据此推荐换掉现有 Codex。

MCP、RAG、Agent：先分清缺的是什么

缺资料、缺接口、缺流程，应该分别处理。

9月5日的图解把工具连接、检索资料和自主执行放在一起比较。MCP 解决标准化接口，RAG 为回答补充检索材料，Agent 负责多步决策与执行。它们可以组合，不是三个互相替代的产品，也不自动保证回答正确。

编辑判断：先定位缺资料、缺接口还是缺流程，再选择组合。

AI 上 Kubernetes：先想清资源边界

实验能跑，与不会挤占其他服务资源，是两件事。

9月4日，Fairwinds 作者在 CNCF 博客讨论 GPU、突发流量和数据边界给平台运维带来的变化。他强调任务放置、利用率与保护措施。这里是工程观点，不是所有 AI 项目都需要 Kubernetes 的结论。

编辑判断：先约束资源影响范围，再增加自动化程度。

🛠️ 工具推荐

实践精选 · 非当日新发布已有能力可用

今日实用工具：domain-modeling Skill

当产品、客户端和后台对同一个词理解不同，Agent 会把歧义一起写进代码。这个 Skill 用具体场景澄清术语，并对照代码检查定义冲突。此前介绍过同一技能库的排障与审查，这次补充的是需求建模能力，不是重复报道该库发布。

适合你的环节：需求评审、接口字段定义、iOS/Android/后台语义对齐。

今天怎么试：可直接说：用 domain-modeling 检查这份需求里“取消、关闭、失效”的区别，列出边界场景；先只分析，不改业务代码。

边界：它帮助发现歧义，不替产品做决定。写入术语表或 ADR 需明确范围；不要上传私有需求到未授权服务。

实践精选 · 非当日新发布已有能力可用

prototype Skill：先验证状态，再写完整页面

把“这个交互到底对不对”变成一个可操作的小实验：只验证一个状态问题或一组界面方案。它不是生成完整 App 的承诺，而是让团队在实现之前看见分歧。已有技能库的另一项具体用法。

适合你的环节：客户端交互评审、边界状态演示和方案选择。

今天怎么试：可直接说：用 prototype 只验证“加载中取消后又重试”的状态流，在隔离目录做最小演示，不接真实接口，不并入业务代码。

边界：产物是一次性验证，不代表生产实现；涉及创建文件、运行或提交时仍按你的授权范围执行。不能替代真实 App 验收。

实践精选 · 非当日新发布方法可试

git range-diff：检查 Agent 第二轮到底改了什么

普通 diff 看最终文件差异，range-diff 比较两组提交对应的补丁。Agent 修完审查意见，或者分支重新整理后，它能帮助你发现漏改、意外变化和提交意图偏移。无需新增开发平台。

适合你的环节：MR 二次审查、rebase 后核对和 Agent 修订验收。

今天怎么试：保留修改前后的真实提交引用，用 git range-diff <base>..<before> <base>..<after> 只读比较；先请 Agent 解释差异，再决定是否接受。

边界：它不是测试，也不是自动证明改动正确。输出供人阅读，不保证跨 Git 版本稳定，不能直接当机器补丁输入；需先明确有效提交范围。

实践精选 · 非当日新发布条件适用

Agent Browser（Talocode）：把网页验收留下证据

这个项目为软件 Agent 提供浏览器检查、截图、控制台和网络观察，并提供 MCP 入口。适合把“页面打开了”推进到可回看的验收证据。来自9月6日的 X 讨论；项目本身不按当天新发布报道。

适合你的环节：Web 页面或发布预览的冒烟检查。

今天怎么试：先选一个无登录、无写操作的测试页面，对照项目文档评估 check、截图和 session report；批准接入后再与现有浏览器结果比较。

边界：默认阻止私网目标和 localhost；本地开发放行要单独配置。README 表明托管云尚未部署，不能当作现成云服务；不能代替 iOS/Android 原生 UI 验收。

实践精选 · 非当日新发布条件适用

OKF Agent Memory：按需找回项目知识

把项目知识拆成有索引的 Git 文件，通过 CLI 或内嵌 MCP 按需检索，目标是减少每次会话重贴长文档。HN 近期讨论带来这条线索；真正可借鉴的是分层读取，不是把全部历史搬进另一个库。

适合你的环节：跨会话交接、项目决策检索和减少重复上下文。

今天怎么试：先用脱敏的小项目知识集评估：能否检索出一项既有决策、来源是否准确、是否读入无关内容；与现有短摘要方法比较后再决定接入。

边界：项目宣传的检索速度、80% Token 缩减和标准兼容性属于项目自述，不能当作本任务实测。需审查记忆写入、敏感信息和陈旧内容；不要默认替换现有记忆机制。

MCP · 实践精选条件适用

Kotlin PSI MCP：查真实引用，不只搜同名文本

通过 MCP 把 IDE 的 Kotlin 语义分析交给 Agent：查引用、跳到定义、探索继承关系。它不是另装一个大 IDE，而是为已有 Android Studio 或兼容 IDE 增加一个小接口。已有项目，本期作为实践精选。

适合你的环节：Android 引用排查、重构前影响分析和审查准备。

今天怎么试：先选择一个 Kotlin 符号，用已有 IDE 记录引用结果；确认插件版本和接入权限后，再用 PSI MCP 查询同一符号，比较是否遗漏。

边界：需要安装插件、重启 IDE、打开正确工程并完成索引，再配置本地 HTTP MCP。未安装或连接验证；跨语言支持有限，不能把它当成所有语言的通用分析器。

🧩 本期概念库

1. 领域语言

一句话解释：团队为同一业务对象使用一致、可用场景检验的术语。

为什么重要：词义不同会变成接口和状态机分歧。

团队应用：评审时先找三个最容易混用的词，对照代码核对。

2. 渐进式上下文

一句话解释：先读索引，只加载当前问题需要的证据。

为什么重要：减少无关文本，也让过期知识更容易识别。

团队应用：交接保留目标、已证实结果和文件指针，不整段复制历史。

3. 补丁之间的差异

一句话解释：比较两轮提交的改动意图，而不只是当前文件快照。

为什么重要：能发现修订或 rebase 引入的变化。

团队应用：MR 二次审查保留 before/after 引用，先读 range-diff 再看重点文件。

4. 观察与判定

一句话解释：截图、引用列表和内存指标是证据，不自动构成质量结论。

为什么重要：单一成功信号可能漏掉重要状态。

团队应用：每个自动化步骤配一个独立验收条件。

🎙️ 播客提纲

让 Agent 少返工，比让它多写代码更有用

Agent 十分钟写完了代码，你却又花半天解释需求、确认状态、找漏改。慢的到底是谁？今天我们把新闻窗口扩到七十二小时，并用七天历史去重。重点不是再列一排大型软件，而是六个能嵌入现有工作的小工具和方法，其中三项已有能力今天就能试。

主故事：重写很快，旧行为却不会自动消失

Simon Willison 在九月六日讨论技术债时，说到一种熟悉的局面：旧系统还在接业务需求，新系统却只覆盖了一部分功能。结果不是旧系统消失了，而是团队同时维护两套系统。这是作者的工程经验，不是行业成功率统计。他更倾向先补自动化测试，再做定向重构。我的判断是，这个问题放到 Agent 开发里同样成立：新代码写得快，不代表需求已经讲清，也不代表原来的边界被保住。与其先换一个更大的开发平台，不如先减少三类返工：名词歧义、状态争议和修订遗漏。今天的工具推荐围绕这三个入口展开。

快讯一：先用你已有的两个 Skill

第一个是 domain-modeling，也就是领域建模。让它检查需求里取消、关闭和失效是否被混用，拿具体场景核对定义。第二个是 prototype，只做一个能回答问题的小原型，例如加载时取消，再立即重试，状态应该怎么走。这两个 Skill 当前会话都已经提供，不需要重新安装。同一个技能库前几天介绍过排障和审查，这次是不同的实际用法，不是重复报道它又发布了。小原型也不是生产代码，先把隔离目录、不接真实接口和不并入业务工程说清楚。

快讯二：用现有 Git 检查第二轮改动

第三个是 git range-diff。普通差异看最终文件，它比较两组提交里的补丁，适合看 Agent 修完审查意见之后，有没有顺便改变原来的意图。本机已经有 Git，这是一种手动工作法。先保留修改前后两个真实引用，再做只读比较。它不能代替测试，输出也不是稳定的机器接口。与其把整段仓库历史重新发给助手，不如先指出这两轮补丁真正不同的地方，把审查范围缩小。

快讯三：三个新接口，先说清接入条件

剩下三项需要接入验证。Talocode 的 Agent Browser 提供网页检查、截图和 MCP 入口，来自这次 X 的工具线索。它不是 Vercel 的同名项目，默认还会阻止私网目标，托管云也不能当作已经上线。OKF Agent Memory 把项目知识放进有索引的 Git 文件，通过检索按需读入。项目宣传的百分之八十 Token 缩减，我们没有实测，不会当作承诺。Kotlin PSI MCP 则借用 IDE 的语义索引查真实引用，需要正确工程与完整索引。它们都没有替你安装，更不该一次全装。

团队行动：只选择一个返工点

今天先选一个最常反复解释的问题：需求不清，就用领域建模；交互不清，就做小原型；修订不清，就比较补丁。新闻区还补了九月四日到六日的可靠性更新，例如 Bun 返回值正确但仍保留内存的回归，以及 Codex 的异步澄清指引修复。它们提醒我们，执行成功只是一个信号，还要检查行为、资源和调用契约。七十二小时扩大的是候选窗口，不是允许重复，也不是每天把三天全文重新读一遍。

这期先做一件小事：把下一次需求里的三个歧义词列出来，让已有 Skill 帮你核对。少一次返工，比多安装一个软件更容易看到收益。需要接入的工具，等真实问题和最小验证都明确后再试。

3
